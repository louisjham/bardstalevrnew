🔴 Critical

These issues can produce incorrect game state, silent data corruption, or hard crashes in regular play.

CriticalBug MessageSpooler — enqueueAndWait resolves too early on concurrent calls
src/core/utils/MessageSpooler.js · lines 63–78

enqueueAndWait registers a 'complete' listener, then calls enqueue(). If the queue was already processing when this is called, enqueue() does not restart the loop (correct), but the onDone guard checks this.queue.length === 0 && !this.isProcessing. Because the earlier batch might drain and fire 'complete' before the newly-pushed messages reach the front, the promise can resolve while messages are still mid-queue or mid-type. In combat with rapid multi-hero actions, the next round can begin before the narrative scroll finishes, breaking the suspenseful action-by-action pacing guarantee.

Fix: Track a per-call "high-water mark" queue position at enqueue time and only resolve when all items up to that mark have been processed, rather than relying on the generic 'complete' event.

CriticalBug Combat engine — back-row member can be melee-targeted when no front-row heroes survive
src/core/combat/CombatEngine.js · lines 854–868 (executeMonsterPhase)

Monster melee targeting first picks a random alive party member (aliveParty[targetIdx]), then checks isInFrontRow. If the back-row member is selected and no front-row member is alive, frontRowAlive will be empty and the code falls through — leaving target pointing at the originally-selected back-row member, which is correct in that edge case. However, the front-row scratch filter also calls this.party.indexOf(p) inside a tight loop over aliveParty, which can grow O(n²) as party size and monster group size increase. More critically, the fallback target is never re-assigned when frontRowAlive.length === 0; a back-row Conjurer can be struck by monsters even when a front-row Warrior is alive — whenever Math.random() happens to pick the back-row index first.

Fix: Build the front-row filter once before the monster loop, and only fall back to back-row targets when frontRowAlive.length === 0.

CriticalBug triggerCinematicIntro — leaked requestAnimationFrame loop on rapid restart
src/world/retro-room/RetroRoom.js · lines 1229–1441 (animateCinematic)

The cinematic loop guards on this.isFlashPaperActive at its top. reset() sets isFlashPaperActive = false, but triggerCinematicIntro immediately sets it back to true before scheduling the requestAnimationFrame. If the user presses [R] (restart) while the cinematic is in any phase other than FADE_IN, the guard fires correctly on the old frame callback. However the outer condition is checked only at the very top of animateCinematic; phases 2–5 use an early-return pattern that calls requestAnimationFrame(animateCinematic) before the guard check executes on the next tick. This means a rapid double-restart schedules two concurrent cinematic loops running in parallel — mutating this.screenOverlay.material.opacity and the floppy disk position from two competing callbacks simultaneously.

Fix: Introduce a unique generation token (e.g., this._cinematicGeneration++) captured by closure in each loop invocation; bail out if the captured token no longer matches the current one.

🟠 High

These cause noticeable gameplay incorrectness or measurable performance overhead on XR hardware.

HighPerformance Main loop — revealTile called 2–3× per frame in SKARA_BRAE_STREETS
src/main.js · lines 1465–1469, 1598–1601

During street exploration, skaraBraeGrid.revealTile(headPos.x, headPos.z) is called in the locomotion block (line 1468), then again inside the SKARA_BRAE_STREETS render block (line 1601), and again via locomotion.update() itself (FreeLocomotion.js line 744). Each call invokes worldToSource — a coordinate transform — and writes to the explored grid. Three identical calls per frame for a no-op that only needs to fire once per tile step.

Fix: Remove the duplicate calls in the main loop; the single call inside FreeLocomotion.update() (which already gates on the grid reference) is sufficient, or promote it to a single post-locomotion call in startLoop.

HighPerformance Center reticle raycast runs full scene traversal every frame when Grimoire is closed
src/main.js · lines 1006–1174 (updateCenterReticle)

updateCenterReticle() is called every frame when not in VR mode and executes up to 4 raycaster.intersectObjects(..., true) calls per frame (Grimoire, state-specific interactables, dialogue mesh, monsters, heroes, buttons). The true recursive flag means Three.js traverses every descendant of every interactable group. In COMBAT_ZONE this can mean traversing monster billboard groups, hero groups, and button groups — 3 full tree walks per frame at 60+ fps on desktop.

Fix: Pre-flatten interactable lists to leaf meshes once (on scene entry) rather than passing parent groups with recursive: true. Additionally, gate updateCenterReticle behind a dirty flag that skips the call when the player hasn't moved or the scene hasn't changed.

HighBug Day/Night HUD DOM query inside the render loop allocates 3 elements per frame
src/main.js · lines 1563–1585

Every frame calls document.getElementById('day-night-icon'), document.getElementById('day-night-text'), and document.getElementById('day-night-services') — three synchronous DOM lookups at 60–90 fps (5,400 DOM queries/sec at 90 Hz VR). These lookups are not expensive per call but they prevent Blink/V8 from inline-caching the result and trigger layout style recalculations whenever .textContent or .className changes.

Fix: Cache these three element references in the constructor (or on first access) as instance properties. Update DOM only when the phase or remaining-seconds value actually changes.

HighBug animateRecruitment — setInterval hop animation leaks if mesh is removed mid-hop
src/main.js · lines 500–523

The patron hop uses setInterval(hop, 16) directly on animTarget.position.y. If the game state transitions away from the Tavern (e.g. the player presses [R] or fills the party while a hop is still in progress), animTarget may belong to a now-invisible or disposed scene graph. The interval continues executing for the remaining ~160ms, writing to a stale object. Additionally, if recruitPatron is called multiple times quickly (e.g. rapid gamepad presses), multiple intervals accumulate on the same mesh, causing erratic vertical jitter.

Fix: Replace setInterval with a small tween tracked in a per-mesh userData.hopInterval slot, clearing the previous one before starting a new one. Alternatively, use the existing renderer.setAnimationLoop tick for animation rather than a detached timer.

HighBug fadeInFromBlack / fadeOutToBlack — parallel requestAnimationFrame loops can fight each other
src/world/retro-room/RetroRoom.js · lines 1631–1672

Both fade methods create their own anonymous requestAnimationFrame loop writing to this.screenOverlay.material.opacity. There is no cancellation handle (cancelAnimationFrame). If fadeInFromBlack is called while a fadeOutToBlack loop is still in flight (e.g. a state transition triggers a fade-in before the preceding fade-out finishes), both callbacks mutate the same opacity concurrently, causing flickering. The main loop also nudges screenOverlay.material.opacity passively (main.js line 1489), creating a three-way race.

Fix: Store the RAF handle and cancel previous animations before starting a new one. Consolidate the passive main-loop nudge into the dedicated fade methods.

🟡 Medium

Correctness edge cases and moderate per-frame waste that accumulates on Quest hardware.

MediumPerformance VR button polling iterates all inputSources every frame instead of using events
src/main.js · lines 1532–1547

The Y/X button toggle for the Grimoire polls xrSession.inputSources with a for loop and checks .pressed state every animation frame. The 400ms cooldown prevents double-fires but the loop still runs every frame (90× per second). The same check is also performed again inside XRManager's own source loop. Prefer xrsession.addEventListener('inputsourceschange', ...) or the existing xr.onSelectStart / onSqueezeStart dispatch to handle this event-driven rather than polled.

MediumBug bestowWeaponClass always creates character with race 'Human'
src/main.js · line 570

When a player recruits patrons in the Tavern, their sprite identity (Paladin, Wizard, Dwarf, Hobbit) is stored in userData.name. When a weapon is later bestowed in Garth's shop, createCharacter(recruit, 'Human', assignedClass) hardcodes the race as 'Human' regardless of the patron identity. A recruited Dwarf patron becomes a Human Warrior, losing racial stat bonuses (Constitution +2, Agility -1, etc.) defined in RaceClassData.js.

Fix: Store both name and race in the recruit queue entry when the patron is clicked (read from TAVERN_TUTORIAL_PATRONS[key].race), and pass it to createCharacter.

MediumBug getObstacles allocates a new array and obstacle objects every frame
src/xr/FreeLocomotion.js · lines 398–439

applyBumperCarCollisions() calls getObstacles(gameState) every frame, which creates a fresh obstacles array and pushes 4–7 new object literals into it. At 90 Hz VR, this generates ~630 short-lived objects per second for GC. The game state only changes on explicit transitions, so the obstacle set is static between transitions.

Fix: Cache the obstacle array as this._obstacleCache keyed by gameState. Rebuild only when this.currentGameState changes (already tracked). This eliminates per-frame allocation entirely.

MediumPerformance LED flicker uses Math.random() from two separate code paths simultaneously
src/world/retro-room/RetroRoom.js · lines 1308–1310 & 1626–1628

During the boot cinematic, the drive LED flicker is driven by Math.random() inside animateCinematic (via RAF). Simultaneously, RetroRoom.update() is called from the main render loop, which also updates driveLedLight.intensity via Math.random() when this.isBooting is true. Both paths write to the same light every frame, meaning two competing random flickering values are applied each frame — only the last writer wins, but both call Math.random() unnecessarily.

Fix: Remove the duplicate flicker from animateCinematic and let update() own all LED animation. Or vice versa — pick one owner.

MediumBug handleStateTransition shows toast on every state change including internal ones
src/main.js · line 378

handleStateTransition unconditionally fires this.showToast("🌌 Transitioning Location: ${newState}") at the top of the method on every state change. This means every time ensureStarterParty() indirectly triggers a party sync that causes setState to re-enter the same state, the toast fires. More visibly, it overlaps with the descriptive toasts each branch fires on its own (e.g. "🍺 Welcome to Skara Brae Tavern!" fires 500ms after the debug transition toast). The debug toast is user-visible pollution in production.

Fix: Remove the debug toast from handleStateTransition or gate it behind a DEBUG flag.

🔵 Low / Polish

Minor correctness gaps and low-impact waste worth a quick fix.

LowBug handleStateTransition(COMBAT_ZONE) re-positions XR rig to origin, discarding street position
src/main.js · line 482

this.xrRig.setPosition(0, 0, 0) is called unconditionally when entering COMBAT_ZONE. On return from combat (onCombatEnd fires setState(TAVERN_INTRO)), the player is teleported to the Tavern rather than back to the street tile they were on. The intended post-combat return is hard-coded to the Tavern, which is by design, but the rig zeroing means that if combat state is entered via a direct HUD button (the "⚔️ 3D Combat" button, line 1000), the rig is also zeroed — which breaks the Grimoire automap position on return.

LowBug Teleporter at (25,2) ↔ (25,7) fires every frame while standing on the tile
src/main.js · lines 1622–1628

The step-on teleporter check runs inside the SKARA_BRAE_STREETS render block every frame and only guards on this._tpCooldown. The cooldown is set to 2000ms. If the player stands still on tile (25,2) or (25,7), the teleporter fires once, the cooldown starts, and re-fires again 2 seconds later while the player is still standing on the exit tile — resulting in a back-and-forth ping-pong every 2s. The teleport should also check that the player has moved off the trigger tile before re-arming.

LowPerformance FLAME spell effect: particle geometry and material re-created on every cast
src/main.js · lines 288–304 (triggerLiveSpellTesting)

Each cast of the FLAME spell allocates a new THREE.BufferGeometry, a new Float32Array(120), a new THREE.BufferAttribute, and a new THREE.PointsMaterial. These are added to the camera and cleaned up 2 seconds later. Repeated rapid casting (e.g. testing from the Grimoire Spellbook tab) grows the activeSpellEffects array and creates GC pressure. A pooled, pre-allocated particle system would serve all FLAME casts.

LowBug _checkRaisedFistAndSteering fallback path uses indexTip.position.length() instead of wrist-relative distance
src/xr/FreeLocomotion.js · lines 334–342

In the Three.js scene-graph fallback (path 2), fist detection computes indexTip.position.length() — the distance of the joint from the scene origin — rather than from the wrist joint, making the fist threshold meaningless in any room-scale scenario where the hand is not near the world origin. The primary WebXR frame path (path 1) correctly uses _jointDist(indexPose.transform.position, wristPose.transform.position). This fallback is exercised in unit tests and in custom rig setups.

Fix: Compute the wrist world position via hand.joints['wrist'].getWorldPosition and measure distance from it, mirroring the primary path logic.
